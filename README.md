# ASBARIX | أسباركس

**منصة داخلية للمصممين والإدارة لإعداد ملفات الطباعة وحساب الخامات والأسعار وإدارة المنتجات والموردين.**

> حالة المشروع: مستخدم داخليًا. ليست خدمة SaaS مفتوحة للجمهور. لا تضع أسرار البيئة أو أسعار شراء العملاء داخل المستودع.

## الوحدات

| الوحدة | وظيفتها |
| --- | --- |
| الأفرخ | حساب توزيع القطع والهالك وتصدير ملفات SVG |
| الاستيكرات والبنرات | تقدير المساحة والكمية وسعر البيع |
| الأكريليك | حساب المقاسات والكمية والتسعير وفق قائمة البيع المعتمدة |
| قوالب الأكواب | قوالب فرد قابلة للتصدير SVG |
| الأوفست والهدايا | كتالوج منتجات جاهزة وأسعار الباقات |
| الباركود | ترقيم المنتجات، مسحها وبطاقات المنتجات وملصقات UBC |
| الموردون والأسعار | البحث والمقارنة والاستيراد والتصدير عبر Excel للإدارة |
| الإدارة | إدارة المستخدمين والسياسات والأسعار والصلاحيات |

تتغير تفاصيل الميزات باختلاف الفرع؛ **النسخة المنشورة هي المرجع التشغيلي وليس الفرع `main` القديم**.

## التشغيل المحلي

يتطلب **Node.js 22** وبيئة متوافقة مع إعدادات Vercel/Redis.

```bash
npm install
npm test
node --test tests/api.test.mjs
node --test tests/product-pricing.test.mjs tests/retail-pricing.test.mjs
npm run build
```

يُنشئ البناء مجلد `public/` من مصادر `src/`. لا ترفع `node_modules/` أو `public/` أو ملفات `.env*` إلى Git.

## هيكل المستودع

- `src/` — صفحات وأصول الواجهة ومولد ملفات SVG
- `api/` — مسارات Vercel العامة والمحمية ونقاط الدخول
- `server/` — منطق التسعير وإدارة المنتجات واستيراد Excel
- `tests/` — اختبارات الحسابات والصلاحيات وواجهات API
- `scripts/monitor/` — فحوص الصحة والأمان الدورية
- `.github/workflows/` — اختبارات GitHub Actions والمراقبة
- `vercel.json` — البناء وإعادة كتابة المسارات وترويسات الأمان
- `docs/RELEASE.md` — سياسة الإصدارات والفحص قبل النشر

## الأمان

الدخول محمي بجلسات مخزنة في Redis وكوكي `HttpOnly`، مع صلاحيات منفصلة للإدارة والمصممين. **لا تعتبر إخفاء الواجهة إجراءً أمنيًا**: تحقّق من الصلاحيات دائمًا في الخادم. احتفظ بمفاتيح `ADMIN_KEY` و`TEAM_CODE` وبيانات Redis وResend وVercel في الأسرار المخصصة، ولا تنسخها إلى Issues أو سجلات CI.

البيانات الحية وأسعار الموردين ليست بيانات اختبار. استخدم قيمًا وهمية في التجارب، ولا تعِد تهيئة Redis الإنتاجية ولا تحذف مفاتيحها من دون نسخة احتياطية.

## إدارة التعديلات والنشر

1. ابدأ أي إصلاح من **آخر commit منشور بنجاح**، وليس تلقائيًا من `main`.
2. أنشئ فرع `fix/*` أو `feature/*` أو `maintenance/*`.
3. افتح Pull Request إلى `production`، وشغّل اختبارات الحسابات وAPI والبناء.
4. راجع Vercel Preview وسجّل فحص الواجهة على الكمبيوتر والجوال ومخرجات SVG وExcel.
5. انشر فقط بعد اجتياز الاختبارات والمراجعة، واحتفظ برابط الرجوع إلى النشر السابق.

**تنبيه:** `main` متأخر تاريخيًا عن كود التشغيل ويحتوي أعمال مراقبة مستقلة؛ لا تستخدمه للنشر أو الاسترجاع حتى تتم تسوية تاريخه. راجع [دليل الإصدار](docs/RELEASE.md).

## المراقبة

راجع [MONITORING.md](MONITORING.md) لتفاصيل فحص الصحة ومهام GitHub Actions والتنبيهات وإعداداتها. فشل اختبارات CI أو نجاح بناء Vercel وحده لا يثبت صحة عملية التسعير على بيانات العمل الفعلية.

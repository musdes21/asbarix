# إدارة الإصدارات — ASBARIX

آخر مراجعة: 2026-11-21. جميع الأوقات في هذا المستند بتوقيت الرياض.

## خط الأساس الحالي

- GitHub: `musdes21/asbarix`
- Vercel project: `montage` — النطاق الإنتاجي `asbarix.vercel.app`.
- آخر إصدار إنتاج موثّق أثناء التدقيق: `06d71d092945767addf07789af33a1575f14ae61` من `fix/approved-acrylic-pricing`، وحالته في Vercel `READY`.
- `production` متأخر بcommit واحد عن هذا الإصدار. **وجود فرع باسم production لا يعني أنه مطابق للإصدار المنشور**.
- `main` متفرع عن خط قديم؛ يحتفظ بملفات مراقبة، ويُعطَّل نشره في `vercel.json`. لا تدمجه في الإنتاج دون مقارنة الملفات ومراجعة أثر إعدادات البناء.

## معيار جاهزية الدمج (DoD)

- [ ] التغيير معزول في فرع من أحدث نسخة إنتاجية موثّقة.
- [ ] لا توجد أسرار أو بيانات عمل حية أو أسعار شراء سرية في التغييرات.
- [ ] نجاح `npm test` واختبارات API والتسعير والبناء.
- [ ] مراجعة كل ملف تغير خصوصًا صلاحيات Redis والأسعار وواجهات التصدير.
- [ ] معاينة Vercel ناجحة، وتحقق يدوي على 390px و1280px.
- [ ] التأكد من أن آلة التسعير لا تعرض تكلفة المورد للعميل.
- [ ] مراجعة Excel import/export وSVG إن مسّ التحديث هذه الوحدات.
- [ ] توثيق SHA المنشور، رابط نشره، وSHA النسخة السابقة القابلة للاسترجاع.

## قواعد دمج الفروع

1. أعد توجيه التغييرات الجديدة إلى `production` **بعد أن تطابق النسخة المنشورة**.
2. أغلق Pull Request القديم بوصف «superseded» فقط عندما تثبت المقارنة أن رأسه موجود أصلًا في الإصدار الأحدث.
3. إذا كان الفرع `diverged` فلا تدمجه تلقائيًا؛ افحص اختلافاته يدويًا وقدّم التغيير المتبقي كـ PR مستقل.
4. أبقِ الفروع التي تحوي تغييرات غير مدمجة حتى يتم اتخاذ قرار بشأنها.
5. لا تحذف المستودعات أو قواعد البيانات أو نشر Vercel القديم بمجرد تنظيف GitHub؛ الاستعادة تتطلب مراجع قابلة للتحقق.

## إجراءات الإصدار والاسترجاع

1. تأكد من نجاح CI وVercel Preview قبل تغيير هدف الإنتاج.
2. انشر SHA محددًا، وليس اسم فرع قابلًا للتغير.
3. افتح `/login` واختبر صلاحيات الفريق والإدارة دون كشف بيانات.
4. اختبر حاسبة الأكريليك بمثال يدوي معروف وسعر رسمي متفق عليه.
5. إذا ظهر خلل: أعد ربط الإنتاج بآخر Deployment معروف سليمًا؛ تجنّب إعادة ضبط Redis.
6. سجّل ما حدث في Pull Request الخاص بالإصدار.

## ديون تقنية معروفة

- `main` لا يطابق كود النشر ويحتاج مصالحة منظمة.
- بعض PRs القديمة متسلسلة على فروع تاريخية؛ ميّز المدمج ضمنيًا من التغييرات المنفصلة.
- اختبارات أدوات مولد الأكريليك القديمة تتوقع ظهور تبويب أخفته متطلبات العمل الحالية؛ لا تضفها إلى بوابة CI حتى يعاد مواءمتها مع سلوك الواجهة المطلوب.
- CSP كامل يحتاج مرحلة Report-Only ومراجعة السكربتات المضمّنة قبل تفعيله.
- راجع تنبيهات `npm audit`، خاصة `exceljs` والاعتمادات العابرة، في فرع منفصل مع اختبار الاستيراد والتصدير.

## التشغيل والمراقبة
